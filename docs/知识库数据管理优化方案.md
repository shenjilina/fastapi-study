# 知识库数据管理优化方案

> 编写日期：2026-10-18
>
> 适用项目：`fastapi-study`
>
> 文档性质：基于当前仓库的现状分析与优化设计，供评审和后续实施使用。
>
> 本次范围：只新增文档；不修改业务代码、数据库、配置或运行时数据。

## 1. 结论与优化目标

当前项目已具备“文件上传 → 创建文档 → 手动触发解析 → 切片 → 向量入库 → RAG 问答”
的基本闭环，并建立了资源归属校验、软删除、审计记录和失败重试入口。
下一阶段建议优先完善数据可靠性，而不是立即拆分微服务或替换全部存储组件。

推荐顺序：

1. **统一规则**：明确文件、文档、知识库的归属关系、统计口径和删除语义。
2. **阻止无效数据参与检索**：即使向量尚未回收，也不得使用已删除、失败或未发布的数据。
3. **实现任务可恢复与写入幂等**：记录任务、租约、处理批次和计划写入的向量 ID。
4. **形成一致性闭环**：将向量清理、源文件回收和数据对账变为可重试的持久任务。
5. **逐步提升管理体验与质量**：增加批量操作、结构化解析、可追溯引用和版本重建。

### 1.1 预期结果

- 每条可检索切片都能追溯到有效知识库、文档、处理批次和源文件元数据。
- 解析失败、进程退出、重复请求和删除操作不会产生长期可检索的孤儿向量。
- 用户能看到排队、处理阶段、失败原因和清理结果，而不是只看到一个状态字段。
- 运维可以发现并修复文件、关系库与 Qdrant 之间的数据差异。
- 在不改变“文件元数据永久留存”的现行业务约束下控制物理文件和派生索引的成本。

### 1.2 边界与假设

- 以本地源代码为现状依据；已有 PRD 是业务约束来源，但其中过时内容需要同步修订。
- 未检查真实用户文件、数据库内容、Qdrant 实例和线上负载，不声称发现了实际脏数据。
- 本文中的风险是静态代码分析所得；性能收益、容量和排期均需实测后确认。
- 外部资料检索未获得可用内容；本文不作库版本兼容性承诺，具体调用方式在实施时核验。
- 不引入多知识库共享同一有效文档、不硬删除 `files` 记录、不默认清空向量集合。

## 2. 当前数据管理现状

### 2.1 实际数据关系

```text
User
 ├── KnowledgeBase（owner_id、visibility、status、deleted_at）
 └── FileRecord（owner_id、源文件位置、摘要、上传/解析状态、存储状态）
          │
          └── Document（file_id、knowledge_base_id、解析结果、deleted_at）
                  │
                  └── Chunk（document_id、内容、顺序、vector_id、deleted_at）
                           │
                           └── Qdrant Point（向量、文本与 metadata）

AuditLog：记录上传、解析、资源变更与向量清理等事件。
ConversationRecord：记录问答和来源文档 ID，但目前没有完整的来源切片版本快照。
```

关键事实：

- `FileRecord` 没有 `knowledge_base_id`，也没有 `deleted_at`。
- `Document.knowledge_base_id` 是当前知识库归属字段。
- 一个文件最多对应一条未软删除文档；软删除历史文档后可以再创建新文档。
- `Document.file_size` 是创建时复制的文件大小，应定义为快照或冗余字段。
- 文档、切片支持软删除；源文件可物理删除，但文件元数据保留。
- 所有知识库切片存放在配置指定的 Qdrant 集合中，通过 metadata 过滤知识库。

依据：[S01]、[S02]、[S03]、[S06]。

### 2.2 当前主流程

| 阶段 | 当前行为 | 已有保障 |
| --- | --- | --- |
| 上传 | 分块读取上传流，写本地目录，计算 MD5，创建文件记录 | 格式白名单、大小限制、空文件检查、按用户查重 |
| 创建文档 | 校验文件所有者和知识库所有者，创建 `PENDING` 文档 | 校验源文件状态、活跃知识库和有效文档唯一性 |
| 提交解析 | 更新文件状态后注册 `BackgroundTasks` | 首次解析与失败重试分别校验状态 |
| 执行解析 | 条件更新抢占文件，解析文本、清洗、切分、文本去重 | 同一待解析文件的任务抢占保护、错误状态回写 |
| 向量入库 | 先写 Qdrant，再创建 SQL 切片并提交成功状态 | 异常时尝试删除已获知 ID 的向量 |
| 问答 | 校验知识库权限和状态，按知识库 metadata 检索 | 知识库隔离、上下文截断、多轮记忆隔离 |
| 删除文档 | 文档与切片软删除，恢复文件状态，后台清理向量 | 保留审计与元数据、提供清理标记 |
| 删除源文件 | 删除磁盘文件，清空路径并更新存储状态 | 不删除文件记录、不覆盖已有解析状态 |
| 删除知识库 | 只设置知识库 `deleted_at` | 普通入口不可再访问，关联数据保留 |

依据：[S04]、[S05]、[S06]、[S07]、[S08]。

## 3. 问题与风险分级

**P0**：优先保障数据安全、隔离与可恢复性。
**P1**：完善一致性、查询效率和管理闭环。
**P2**：在实际需求和质量评估基础上扩展能力。

| 优先级 | 问题或风险 | 当前代码证据 | 影响与建议 |
| --- | --- | --- | --- |
| P0 | 删除与检索缺少即时一致性保障 | 检索仅按知识库过滤；文档删除后的向量清理异步执行 [S05][S06][S07] | 清理前旧切片可能进入问答；在组装上下文之前批量校验 SQL 有效状态 |
| P0 | 入库不是跨存储原子事务 | 先 `add_texts()`，后提交 SQL 切片；异常只补偿已获知 ID [S05] | 进程退出或部分写入报错可能留下孤儿向量；采用持久批次、确定性 ID 和对账 |
| P0 | 后台任务不持久，恢复不自动调度 | 任务在进程内注册；启动只重置解析状态 [S05][S08] | 重启后需要重新提交；改为持久任务、租约与到期回收 |
| P0 | 多实例启动可能干扰有效任务 | 恢复逻辑全量重置 `PARSE_PENDING/PARSING`，没有 worker 租约 [S08] | 一个实例启动可能重置另一个实例正在执行的任务；只接管过期租约 |
| P0 | 原始上传文件没有独立持久卷 | Compose 仅挂载数据库目录与日志目录，默认上传目录为 `./uploads` [S09] | 容器重建存在源文件丢失风险；显式挂载上传目录并纳入备份 |
| P0 | 嵌入后端可能与配置预期不同 | 非本地路径直接使用 hash fallback；集合缺失时才探测维度 [S06][S09] | 学习兜底不应作为正式语义索引；生产显式校验后端、模型与维度 |
| P1 | PRD 的知识库归属规则与代码冲突 | PRD 要求从文件获取归属；迁移已删除文件的知识库字段 [S03][S11] | 容易错误恢复旧关联规则；以当前文档归属模型修订 PRD |
| P1 | 汇总口径含混且重复扫描 | `file_count` 与 `valid_document_count` 使用相同未删除文档计数 [S07] | 并非必然计数错误，但无法表达“已上传未关联”和“可检索”；拆分指标并条件聚合 |
| P1 | 文件查重缺少并发数据库兜底 | 按用户与 MD5 查重，但没有相应唯一约束 [S01][S04] | 并发上传可能重复入库；明确摘要和存储状态唯一性策略 |
| P1 | 清理失败没有持久重试与诊断 | `cleanup_vectors()` 异常只回滚，依赖 SQL 中已保存的 ID [S05] | 漏清理难追踪；增加清理任务、错误记录及按 metadata 补偿 |
| P1 | 源文件删除与数据库状态非原子 | 先 unlink，再提交元数据；上传仅捕获 `AppException` [S04] | I/O 或数据库异常可能导致状态差异和遗留文件；引入待删除任务、暂存与对账 |
| P1 | 长任务终态校验不足 | 最后重开会话只检查有效文档存在和文件 `PARSING` [S05] | 未验证原文档、批次、租约及知识库删除状态；增加提交栅栏 |
| P1 | 解析丢失结构和来源位置 | `clean_text()` 压缩所有空白；解析输出主要为单一字符串 [S12] | 页码、标题、段落等难溯源；保存结构化解析结果后再切片 |
| P2 | 重建索引与历史引用缺乏版本 | 文档和切片没有处理批次、模型快照和发布版本 [S01][S06] | 无法安全重建、回滚及精确复现引用；引入版本化批次和来源快照 |

### 3.1 不应误判的问题

1. **评分方向并非当前已确认缺陷。** Qdrant 集合使用 `COSINE`，封装已将检索分数转换为
   `1.0 - score`，RAG 再按距离越小越好过滤。需要纠正的是配置注释里的“L2 距离”描述，
   并验证阈值与实际模型、集合度量一致；不能直接反转现有比较符号。[S06][S09]
2. **有效文档不等于解析成功文档。** 当前“有效”主要指未软删除且参与唯一约束的文档。
   如果业务想表达可以问答，应增加“可检索文档数”，不能悄悄改变旧字段含义。[S01][S07]
3. **已有任务抢占，但不是完整任务系统。** `process_file()` 的条件更新值得保留，
   但它不覆盖可靠投递、过期租约、任务历史与自动重试。[S05]
4. **已有按 metadata 删除能力。** 优化可以复用 `delete_by_metadata()`，
   不需要重新发明 Qdrant 删除接口。[S06]

## 4. 推荐架构与取舍

### 4.1 三种路径

| 路径 | 内容 | 适用情况 | 取舍 |
| --- | --- | --- | --- |
| A：最小加固 | 保留进程内后台任务，增加检索校验、日志、上传卷和定期扫描 | 短期学习演示 | 改动小，但不能充分解决重启和多实例可靠性 |
| B：渐进可靠化（推荐） | 保留分层代码，增加 SQL 持久任务、处理批次、独立 worker 与对账 | 当前项目持续演进 | 新增组件有限，可先解决关键数据可靠性问题 |
| C：完整平台化 | 外部队列、对象存储、关系库扩容、权限协作与完整版本管理 | 经验证的多用户或大批量需求 | 运维和迁移成本高，不建议一次性推进 |

本方案采用 **B**：先把数据协议和任务协议做好，再根据实测情况选择外部队列、
PostgreSQL 或对象存储。更换存储并不能自动解决幂等、删除和可检索性问题。

### 4.2 目标数据分工

```text
API：鉴权、业务校验、SQL 事务、持久任务记录
                 │
                 ▼
数据库：业务事实、批次、任务租约、发布版本、删除标记、审计
                 │
                 ▼
Worker：解析 → 切片计划 → 向量写入 → 校验 → 发布
                 │                        │
                 ▼                        ▼
源文件存储：可恢复的原始材料       Qdrant：可重建的派生检索索引

问答：知识库访问校验 → 候选检索 → SQL 有效性校验 → 上下文/引用 → 生成
运维：对账扫描 → 异常报告 → 经授权补偿 → 再验证
```

核心原则：SQL 管理业务有效性，Qdrant 管理候选检索，源文件用于重建和审计；
三者之间用明确协议实现最终一致性，不宣称存在一个跨存储原子事务。

## 5. 数据模型与业务规则优化

### 5.1 保留并统一资源边界

| 实体 | 负责的数据 | 不应承担的职责 |
| --- | --- | --- |
| `FileRecord` | 用户上传资产、内容摘要、原始大小、存储位置与状态 | 知识库归属、多个文档版本的执行进度 |
| `Document` | 知识库归属、标题描述、逻辑删除、当前发布批次 | 所有历史执行尝试的错误和耗时 |
| `Chunk` | 指定批次的片段、顺序、来源位置与向量映射 | 自行决定所属知识库或绕过文档权限 |
| `ProcessingRun`（拟新增） | 一次处理批次、配置快照、质量结果和发布情况 | 同一个批次里的每次 worker 重试日志 |
| `ProcessingJob`（拟新增） | 调度任务、尝试次数、租约和下一次执行时间 | 独立覆盖文档的业务有效性 |
| `AuditLog` | 操作主体、请求/任务关联、变更与脱敏结果 | 保存完整原文、凭证和所有调试堆栈 |

短期保留现有文件解析状态以兼容客户端；增加统一状态转换函数并定义状态配对规则。
后续将任务进度交由 `ProcessingJob/ProcessingRun`，避免文件状态变成多版本状态集合。

### 5.2 拟新增字段与实体

以下均为**设计建议，尚未实现**，最终字段以评审和迁移验证为准。

| 位置 | 建议字段 | 用途 |
| --- | --- | --- |
| `files` | `content_sha256`、`storage_backend`、`storage_key` | 内容校验与查重、减少绝对路径耦合 |
| `documents` | `active_run_id`、`revision` | 当前发布批次与乐观并发控制 |
| `processing_runs` | `id`、`document_id`、`generation`、`status` | 管理一次逻辑重建及其输出 |
| `processing_runs` | `parser_version`、`splitter_config`、`embedding_spec`、`content_hash` | 复现解析、切片与嵌入配置 |
| `processing_runs` | `expected_chunk_count`、`published_at`、`created_at` | 完整性检查与发布追踪 |
| `processing_jobs` | `id`、`kind`、`run_id`/目标资源 ID、`idempotency_key`、`status` | 幂等投递和任务类型区分 |
| `processing_jobs` | `attempts`、`max_attempts`、`next_run_at` | 重试预算与退避 |
| `processing_jobs` | `worker_id`、`lease_token`、`lease_expires_at`、`heartbeat_at` | 防止重复执行与旧 worker 提交 |
| `processing_jobs` | `stage`、`error_code`、`error_summary`、`started_at`、`finished_at` | 进度、诊断和耗时 |
| `chunks` | `run_id`、`content_hash`、`page_start/end`、`section_path`、`source_offset` | 版本隔离、位置溯源和去重 |
| Qdrant metadata | `knowledge_base_id`、`document_id`、`run_id`、`chunk_id`、`chunk_index` | 候选归属与 SQL 校验 |
| 来源关联/快照 | 对话 ID、文档 ID、批次 ID、切片 ID、位置、标题及引用摘要 | 历史答案可复现与审计 |

`embedding_spec` 至少记录实际后端、模型标识、模型版本或文件指纹、维度及距离度量。
不能只记录用户配置的模型名称，因为实际后端可能是 fallback。

`run` 表示稳定的逻辑处理批次，`job.attempts` 表示执行尝试；自动重试同一批次时，
应复用该批次的计划输出和向量 ID。输入或配置变化时才创建新批次。

### 5.3 唯一性与索引

建议在实施前检查重复数据并通过查询计划验证：

- 保留“每个文件最多一条未删除文档”的部分唯一约束；不要改成按知识库唯一。
- 保留现有 MD5 字段以兼容客户端，逐步回填 SHA-256。内容摘要不承担鉴权用途。
- 可对仍处于 `PRESENT` 的文件增加 `(owner_id, content_sha256)` 条件唯一约束，
  避免同一用户并发上传重复内容；物理删除后的重新上传应允许。
- 若未来引入暂存状态，只对已发布的可用文件实施上述唯一约束，另外控制上传幂等键。
- `processing_jobs.idempotency_key` 唯一；同一目标与同一批次的重复提交返回已有任务。
- `(document_id, generation)`、`(run_id, chunk_index)` 唯一；为有效 `vector_id` 设置唯一策略。
- 文档列表优先评估 `(knowledge_base_id, deleted_at, created_at, id)`，
  有状态筛选时另行评估复合索引，避免盲目叠加所有排列组合。
- 任务调度评估 `(status, next_run_at)`，切片读取评估 `(run_id, deleted_at, chunk_index)`。
- Qdrant 根据实际过滤需求建立 metadata 字段索引，并用真实样本验证收益。

当前唯一索引声明带有 `sqlite_where`，迁移历史也包含 SQLite 专用逻辑；
切换数据库前必须验证目标方言的条件唯一索引、外键、枚举和迁移行为，
不能假设仅更改 `DATABASE_URL` 就完成兼容。[S01][S03]

### 5.4 统计口径

| 指标 | 建议定义 |
| --- | --- |
| `activeDocumentCount` | 当前知识库中未软删除文档数，包含待解析和失败文档 |
| `associatedFileCount` | 上述文档关联的不同 `file_id` 数；当前约束下可能等于文档数 |
| `searchableDocumentCount` | 未删除、当前发布批次有效且完整的文档数 |
| `pendingDocumentCount` / `parsingDocumentCount` | 按待处理与执行中状态计数 |
| `failedDocumentCount` | 未删除且解析失败文档数；重建失败但旧版仍有效应另行展示 |
| `activeChunkCount` | 当前发布批次下有效切片数 |
| `sourcePresentFileCount` | 当前关联文件中源文件仍存在的数量 |
| `cleanupPendingCount` | 未完成的向量或源文件回收任务数 |
| `unassignedFileCount` | 当前用户未关联有效文档的文件数，属于文件中心，不归某个知识库 |

短期保留 `fileCount/validDocumentCount` 并明确其旧含义，新增字段表达新口径。
统计尽量采用条件聚合；分页固定使用 `created_at + id` 稳定排序。
只有实测聚合成为瓶颈后才引入缓存或汇总表，并配套失效与重建策略。

## 6. 解析任务、幂等与一致性

### 6.1 任务生命周期

```text
QUEUED → RUNNING → SUCCEEDED
              ├→ RETRY_WAIT → RUNNING
              ├→ FAILED（重试预算耗尽或不可重试）
              └→ CANCELLED（资源失效或明确取消）

RUNNING 且租约到期 → 重新排队/重试；未到期的其他 worker 任务不受启动影响。
```

- 入队时在**同一个 SQL 事务**中更新业务状态、创建任务和写审计记录。
- worker 条件更新抢占任务，取得新的 `lease_token`，定期续租。
- 成功、失败和补偿操作必须带租约校验；旧 worker 不得覆盖新状态或删除接管任务的输出。
- 短期 worker 可扫描数据库持久任务；如果后续使用外部消息队列，增加事务 outbox，
  由投递器发送任务，消费者按任务 ID 幂等处理。
- 不承诺 exactly-once；采用至少一次执行与幂等写入。
- 短暂网络失败可退避重试；格式不支持、文件损坏、权限失效等不无限重试。
- 超时、退避与并发上限作为配置，以压测结果确定，不在本文固定生产数值。

### 6.2 推荐入库协议

1. **校验并抢占**：固定文档 ID、批次 ID、输入摘要和配置快照；验证文件存储状态及租约。
2. **解析与质量检查**：生成结构化文本，记录页数、字符数、空页和异常情况。
3. **先保存切片计划**：以 SQL 事务保存本批次切片及预期向量 ID，状态为未发布。
4. **确定性向量写入**：使用合法 UUID，例如由批次 ID、切片序号和内容摘要生成 UUIDv5；
   同一批次重试复用 ID，避免随机 ID 重复插入。写入语义在目标客户端版本验证。
5. **完成性检查**：检查计划切片与向量映射完整、返回数量匹配，必要时按 ID 验证存在性。
6. **带栅栏发布**：在 SQL 事务中校验文档未删除、原批次仍有效、输入未改变和租约有效；
   更新 `active_run_id`、成功状态、计数、审计记录。
7. **回收旧索引**：发布后登记旧批次清理任务；新批次发布失败时旧版不受影响。

原始文本、切片计划和向量都可以在发布前存在，但不能进入正式问答上下文。
Qdrant 的 `ready` 等 payload 标记可以作为优化，不能作为唯一正确性保障：
SQL 发布与 payload 更新仍可能不同步。

### 6.3 失败与崩溃处理矩阵

| 故障窗口 | 恢复依据 | 处理策略 |
| --- | --- | --- |
| SQL 入队成功，尚未启动 worker | 持久任务 `QUEUED` | 继续调度，重复请求返回原任务 |
| 解析中进程退出 | 过期租约和批次状态 | 重新执行或从持久阶段继续，不能重置所有任务 |
| Qdrant 部分写入后接口报错 | SQL 中的计划 ID 与批次 metadata | 重试同批次写入，或按批次清理；不依赖接口完整返回 ID |
| 向量完成，SQL 发布失败 | 未发布批次和计划切片 | 重试发布或回收本批次，检索校验继续排除它 |
| 处理期间文档或知识库删除 | SQL 删除标记与租约栅栏 | 禁止发布，登记本批次清理任务 |
| 旧 worker 在新 worker 接管后完成 | `lease_token` 不匹配 | 拒绝提交，避免覆盖现任务或误删新批次 |
| 清理时 Qdrant 不可用 | 未完成的清理任务 | 退避重试；不能提前标记清理成功 |

知识库禁用/归档沿用原 PRD 的主要规则：拒绝新任务，排队任务可取消，已执行任务可完成；
知识库**删除**则不允许发布新结果。短期应补上 `knowledge_base.deleted_at` 校验，
并在最终提交时校验原文档身份；版本化后进一步校验批次与租约。[S05][S11]

## 7. 检索有效性与引用追溯

### 7.1 候选不等于可用上下文

统一为普通问答和流式问答提供以下链路：

1. 从已认证身份获取用户，检查目标知识库未删除、权限允许且可问答。
2. Qdrant 按目标知识库检索候选，返回点 ID、切片 ID、文档 ID 和批次 ID。
3. 通过一次或少量批量 SQL 查询校验候选，不逐片段产生 N+1 查询。
4. 只接纳满足以下条件的候选：
   - 知识库与请求一致且未删除；
   - 文档与知识库一致、未删除并已有有效发布结果；
   - 切片未删除，且属于该文档当前发布批次；
   - 向量 ID、切片 ID 和版本映射一致。
5. 有效候选再做评分阈值、去重、排序、上下文截断和引用生成。

SQL 校验失败时应安全返回错误或无可用知识提示，不能直接使用未经校验的候选。
短期尚无批次字段时，至少校验 `Document.deleted_at`、`parse_status == SUCCESS`、
`Chunk.deleted_at`、文档归属和向量映射；新协议发布后再要求 `active_run_id`。

### 7.2 过滤后的召回数量

删除旧版本或过滤失效候选可能导致最终条数少于 `top_k`，建议：

- 小幅扩大候选数量，并设置总候选上限和请求时间预算。
- 有需要时执行有限次数补查，避免无限循环和无界扫描。
- 定期清理失效向量，记录候选淘汰比例；不能只靠永久扩大召回弥补脏索引。
- 所有候选不合格或低相关时返回明确兜底，不强制保留失效/低相关切片。

当前 RAG 在所有分数超阈值时会保留距离最小的一条，建议将这一行为改为明确、
可配置的低置信度策略，并增加回归测试；它与数据有效性校验是两个独立问题。[S06]

### 7.3 结构、评分与来源

- 解析层返回段落/页面对象，保留页码、标题和必要的表格结构；切片后再做局部清洗。
- 针对 Markdown、PDF、DOCX 分别定义结构策略，扫描 PDF 是否需要 OCR 另行评估。
- 文本去重保留出现位置，不能仅删除重复片段后丢失所有出处。
- 评分字段明确为余弦相似度或 `1 - cosine_similarity` 距离，禁止与 L2 名称混用。
- 使用真实中文问题集校准阈值、切片长度和重叠参数；hash fallback 只用于学习/离线兜底。
- 引用保存文档/批次/切片 ID、页码或章节及当时标题，必要时保存受控的引用摘要。
- 已删除或不可见来源的历史展示必须遵守权限策略，不自动暴露保留的正文。
- 私有化/删除之后，是否需要终止正在生成的流式回答属于更强撤权语义；
  应明确产品要求，并在上下文使用、流式来源输出等关键边界做必要复检。

## 8. 删除、源文件保留与回收

### 8.1 分开定义四种操作

| 操作 | 立即生效的业务行为 | 后续任务 | 保留内容 |
| --- | --- | --- | --- |
| 删除文档 | 文档与切片软删除，停止检索，禁止发布，取消关联任务 | 清理该文档各批次向量 | 文件记录、文档/切片历史、审计 |
| 删除源文件 | 按规则停止需要原文件的处理，登记待删除状态 | 安全删除物理文件，提交实际存储状态 | 文件元数据和已有解析结果 |
| 删除知识库 | 设置知识库删除标记，禁止访问、新任务和新结果发布 | 取消任务；是否回收派生索引按策略执行 | 保留关联文件、文档、切片和审计 |
| 历史索引回收 | 只处理已确认不再发布的旧批次 | 删除目标批次向量并验证 | 文档、版本与审计信息 |

不得把“删除源文件”当作“撤回知识内容”：当前两者语义不同。
如果用户希望内容停止问答，应删除文档或下线知识库，而不只是删磁盘文件。

原 PRD 要求删除知识库时保留关联数据。本方案不改成级联硬删除或自动删除源文件；
是否在保留审计记录的前提下回收其派生向量，应由业务确认并配置保留策略。

### 8.2 清理任务闭环

- 软删除事务中同时创建清理任务；API 返回任务 ID 与“待清理”，不是“已清理”。
- 按文档/批次 metadata 删除，必要时结合已知点 ID 删除，覆盖未成功回写 SQL 的向量。
- 必须验证删除完成，才标记该目标清理成功；失败保留错误、重试时间和告警。
- `vector_cleaned` 短期保留兼容，长期由清理任务汇总得到，避免一个布尔值覆盖多批次状态。
- 重试老文档的清理不能删除新文档或新发布批次；禁止用不含目标范围的集合清空操作。
- 任何回收动作保留任务、操作主体、范围、数量及结果，支持审计。

### 8.3 上传与源文件一致性

建议上传使用暂存目录和发布流程：流式写暂存文件 → 校验 → 保存待发布元数据 →
原子移动到最终路径（条件允许时）→ 标记可用。
这些步骤仍非跨文件系统与 SQL 的原子事务，应通过状态与对账补偿中断窗口。

源文件回收采用“SQL 创建待删除任务 → worker unlink → 回写完成”的流程。
待删除期间禁止创建需要原文件的新任务；文件已不存在时幂等确认，而不是重复失败。

安全要求：

- 只删除经规范化且位于配置存储根目录内的路径；拒绝越界路径及不安全的符号链接。
- 原始上传名称仅作展示；继续使用服务器生成的存储名称。
- 同时处理 I/O、权限、数据库唯一冲突和提交异常，留下可恢复记录。
- 文件记录、审计记录不得因普通回收任务被删除；调试重建数据库脚本不能用于生产清理。

## 9. 数据质量、对账与运维

### 9.1 最小对账规则

| 对账项 | 异常判定 | 修复原则 |
| --- | --- | --- |
| 文件元数据 ↔ 物理文件 | `PRESENT` 但文件缺失，或存储目录出现无归属文件 | 报告缺失；无归属文件先隔离并等待确认，不直接删除 |
| 文档 ↔ 切片 | 当前发布批次的有效切片数与记录计数不同 | 重新计算/重新处理，保留原始差异报告 |
| 切片 ↔ 向量 | 已发布切片对应点缺失 | 登记修复任务；按比例/策略暂停受损版本检索 |
| 向量 ↔ 文档/批次 | 指向删除、不存在或长期未发布批次 | 隔离并按保留策略清理 |
| 任务 ↔ 租约 | `RUNNING` 租约到期或重试预算耗尽 | 接管到期任务或转人工处理 |
| 摘要 ↔ 源文件 | 文件仍存在但内容摘要不同 | 禁止沿用旧版本，调查修改来源 |

对账需区分正在处理的暂存数据与真正孤儿：对有效租约、近期未发布批次设置宽限期，
清理前重新校验状态，避免扫描器与正常入库竞态。执行修复支持 dry-run、分页、限速、
检查点和结果复查；不因一次远端查询失败就认定数据不存在。

### 9.2 可观测性

建议记录和展示：任务排队时长、阶段耗时、成功率、重试次数、清理待办数量与最老年龄、
孤儿向量数量、发布数据缺失率、检索候选淘汰率、实际嵌入后端和存储容量。

应用请求与后台任务通过 `request_id/job_id/run_id` 关联。当前审计模型已有
`request_id`，但 `record()` 未接收该参数，后续应贯通请求和后台执行上下文。[S13]

用户响应使用稳定 `error_code` 和脱敏原因；堆栈、绝对路径和原始第三方错误留在受控日志。
不要将任务 ID、文件名等高基数字段作为指标标签；这些字段放在日志和追踪中。

### 9.3 备份、部署与恢复

- Compose 增加上传目录持久卷，并显式设置 `FILE_STORAGE_DIR` 指向挂载目录。
- 备份范围包含关系库、源文件、Qdrant 快照/可重建材料、索引配置与模型指纹。
- 记录备份一致性时间点；一致性要求较高时暂停发布并等待任务稳定再备份。
- 恢复演练先在隔离环境执行：恢复 SQL → 恢复源文件 → 恢复/重建索引 → 对账 → 开放请求。
- 不复制真实 JWT 密钥或模型凭证到文档，配置备份采用受控的秘密管理机制。
- 生产迁移使用 Alembic，并测试完整迁移链；`create_all()` 不能替代已存在表的结构迁移。
- 明确 RPO/RTO、备份频率与告警阈值后再落具体配置，本文不虚设已达成指标。

## 10. API 与管理体验

### 10.1 保持现有项目约定

继续复用 `ApiResponse`、认证依赖、分层 service/crud 和 `ApiBaseModel` 的 camelCase 别名。
本轮设计不要求重写现有 POST 风格接口；新增协议优先兼容旧客户端。

| 能力 | 建议接口形态（未实现，默认前缀 `/api`） | 响应要点 |
| --- | --- | --- |
| 提交/重试解析 | 扩展 `POST /api/documents/parse` | `jobId`、`runId`、业务状态、是否复用任务；新增异步协议可采用 202 |
| 任务详情 | 新增 `POST /api/document-jobs/detail` | 阶段、尝试次数、错误码、时间，不向用户暴露内部租约 |
| 批量操作 | 新增 `POST /api/documents/batch-action` | 每项结果、失败原因、任务 ID、成功/失败/跳过汇总 |
| 统计 | 扩展 `POST /api/knowledge-bases/summary` | 区分有效、可检索、失败、源文件和清理统计 |
| 文档删除 | 扩展 `POST /api/documents/delete` | 已软删除、清理任务 ID、清理状态 |
| 管理对账 | 新增受限的管理员/运维入口或 CLI | dry-run、范围、差异与修复任务，不开放普通用户全局访问 |
| 版本重建 | 后续新增 `POST /api/documents/rebuild` | 新批次 ID；成功后才替换已发布版本 |

### 10.2 批量操作规则

- 每项独立校验权限和状态；避免一个失败导致整批已接受任务丢失。
- 设置批量上限和单用户任务并发限额，分页入队，不一次加载所有失败文档。
- 重复提交返回已存在任务，不能不断创建重复解析或清理。
- 用户能区分“新批次失败，但旧版仍可用”和“首次解析失败，无可用内容”。
- 公开知识库读取权限不等于编辑权限；运维全局入口另行定义角色与审计。

## 11. 实施顺序与迁移方案

### 11.1 阶段一：现状对齐与风险止血

范围：统一文档归属和统计定义、增加检索有效性校验、补齐任务删除状态复检、
挂载上传持久卷、记录清理异常、明确生产嵌入后端策略。

验收：

- 不因异步向量清理延迟而将已删除文档用于普通或流式问答。
- 在控制测试中，任务开始前已删除的知识库不再解析，删除中的批次不能提交成功结果。
- 容器重建测试后原始上传文件仍可访问；此项需实际部署环境验证。
- 明确有效文档与可检索文档口径，保留旧字段兼容。

### 11.2 阶段二：可靠任务与一致性闭环

范围：增加任务、批次与租约，建立持久切片计划、确定性 ID、清理重试及对账工具。

验收：

- 在各故障窗口退出 worker 后，任务可重新接管且不重复发布。
- 重复请求、重复消费和部分向量写入不会增加同批次的有效向量数量。
- SQL 发布失败时未发布数据不进入问答；Qdrant 恢复后清理任务可自动完成。
- 多 worker 启动不重置未过期任务；旧租约无法提交。

### 11.3 阶段三：管理与质量提升

范围：批量任务与进度、结构化解析、来源快照、质量评估和版本化重建。

验收：重建失败保留旧版；新版本只在完整校验后发布；历史引用可识别原批次和来源位置；
真实问题集能对不同切片及模型方案做可重复比较。

### 11.4 安全迁移步骤

1. 备份并盘点：迁移 revision、文件数量、文档状态、切片和向量差异、重复摘要。
2. 修订 PRD 的旧归属规则和术语，明确新协议与旧客户端兼容方式。
3. 采用扩展式迁移：先增加可空字段和新表，不立即删除旧状态/MD5 字段。
4. 给已成功文档建立 `legacy` 批次，绑定现有切片；保留原向量 ID，不强制全量重算。
5. 在源文件仍存在时回填 SHA-256；物理删除文件不能伪造摘要，可保留未回填状态。
6. 分批补齐 Qdrant metadata；过渡期检索先使用旧映射的 SQL 校验，覆盖完成后再收紧过滤。
7. 灰度启用新任务、发布和清理协议，执行对账及故障注入测试。
8. 数据满足约束后再创建严格唯一索引/非空约束；最后淘汰不再使用的旧协议。

旧代码不能在新租约协议启用后继续写任务状态。功能回退优先关闭新任务投递或发布，
保留新增表和字段，避免盲目 downgrade。特别是移除文件知识库字段的现有迁移
`20260823_0010` 已明确不支持自动恢复旧字段，回滚需单独设计。[S03]

| 工作项 | 主要代码位置 |
| --- | --- |

## 12. 测试与验收清单

### 12.1 必须新增的回归测试

| 场景 | 预期结果 |
| --- | --- |
| 同一用户并发上传相同内容 | 一个可用文件资产，其余返回重复结果，磁盘无重复正式文件 |
| 同一文件并发创建文档 | 只有一条有效文档；唯一冲突转为受控业务响应 |
| 多次提交同批次解析 | 复用任务；切片与向量数量不膨胀 |
| worker 重启及多实例启动 | 到期任务可恢复，其他有效租约不被重置 |
| 部分向量写入后报错 | 计划 ID 可追踪，重试或清理后无长期孤儿 |
| 向量已写但 SQL 发布失败 | 未发布切片不进入问答，恢复后可发布或回收 |
| 解析中删除知识库/文档 | 不能发布到已删除资源，目标批次清理可重试 |
| 删除成功但向量暂未清理 | 普通及流式回答均不使用旧切片 |
| 旧批次/跨知识库 metadata 候选 | SQL 校验剔除，不能绕过权限或发布版本 |
| Qdrant 清理失败后恢复 | 清理状态不提前成功，重试完成后能验证为零 |
| 源文件删除后解析内容仍存在 | 遵循独立删除语义；源文件不能再用于重建 |
| 文件已删除但 SQL 提交失败 | 对账或幂等任务能修复，元数据永久保留 |
| 重建失败和版本切换 | 旧发布版继续可用，成功后才切换新批次 |
| 所有候选失效或低相关 | 返回明确兜底，不能强行使用被剔除候选 |
| 统计与版本迁移 | 各指标口径正确，历史切片和原向量 ID 不丢失 |
| 备份恢复和真实 Qdrant 验证 | 隔离恢复后通过对账，覆盖真实点 ID/删除/度量行为 |

单元测试使用 fake store 或内存数据库覆盖状态与故障窗口；真实 Qdrant 集成测试验证
合法点 ID、payload、重试写入、删除及评分行为，不能只依赖内存模式结果。
迁移同时覆盖 `create_all()` 的模型结构和 Alembic 升级后的实际结构，
并验证 SQLite 外键是否被实际启用；声明了外键不代表运行时一定强制检查。[S08]

## 13. 需要评审确认的决策

以下不影响先开展 P0 加固，但会影响后续协议与排期：

1. `validDocumentCount` 是否继续表示未删除文档；建议保留，并新增可检索指标。
2. 删除知识库后派生向量的保留期限；默认保留 SQL 历史和文件元数据，不删源文件。
3. 私有化/删除是否要求立即终止已开始的流式回答，还是仅禁止后续请求。
4. 生产嵌入模型的实际本地部署方式、缺失时的失败策略，以及中文质量评估集。
5. 当前文件“一条有效文档”规则是否长期保持；本方案默认保持。
6. 队列并发规模、源文件保留策略、运维角色和备份 RPO/RTO。
